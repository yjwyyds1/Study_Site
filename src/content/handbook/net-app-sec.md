## 本篇总览（NET-41 ~ NET-50）

用户在浏览器敲下 `https://example.com` 到屏幕亮起网页，背后悄悄穿过 **DNS 解析 → TCP/QUIC 握手 → TLS 加密认证 → HTTP 报文交换 → 负载均衡转发**。本篇系统拆解应用层协议演进与网络安全底线（`NET-41` ~ `NET-50`）。

---

## 一、DNS 层次架构与递归/迭代查询（NET-41）

全球几十亿域名怎么做到几毫秒内查到 IP？靠一棵倒挂的分布式树：
- **本地缓存 → `/etc/hosts` → 递归解析器（运营商 / `8.8.8.8` / `223.5.5.5`）**；
- 如果递归解析器也没有缓存，它就替你展开**迭代查询**：先问全球 **13 组根服务器（`.`）**“`.com` 归谁管？” → 再问 **`.com` 顶级域（TLD）**“谁管 `example.com`？” → 最后问 **`example.com` 权威域名服务器**拿到准确 IP！

## 二、DNS 常见记录类型、TTL 与常见坑（NET-42）

| 记录类型 | 作用 | 示例 |
| --- | --- | --- |
| **`A` / `AAAA`** | 域名映射到 IPv4 / IPv6 地址 | `example.com -> 93.184.216.34` |
| **`CNAME`** | 域名别名（指向另一个域名，如挂 CDN） | `www.example.com -> edge.cdn.net` |
| **`MX` / `TXT`** | 邮件服务器地址 / 任意文本认证（域名所有权验证 SPF） | `v=spf1 ...` |
| **TTL 陷阱** | 缓存有效期（秒）。上线迁移服务器 IP 前，**提前一天把 TTL 从 86400 调小到 60 秒**，否则老用户缓存一天切不过来！ |

## 三、HTTP/1.1 报文结构、方法幂等性、状态码与 Keep-Alive（NET-43）

```text
GET /api/logs?level=ERROR HTTP/1.1\r\n     ← 请求行: 方法 + URI + 协议版本
Host: logs.example.com\r\n                 ← 首部: 虚拟主机必填！
Connection: keep-alive\r\n                 ← 复用当前 TCP 长连接
\r\n                                       ← 空行标志首部结束！（后面是可选 Body）
```

- **幂等性（重试会不会出事故？）**：`GET`（查）、`PUT`（全量覆盖）、`DELETE`（删）连续执行 10 次结果一致，**天然幂等**，超时可安全重试；`POST`（创建订单/扣款）**不幂等**，断网重发必须靠业务幂等键防扣两次钱！
- **状态码五大类**：`2xx` 成功（`200/204`）、`3xx` 重定向（`301` 永久 / `302/307` 临时 / `304` 走本地缓存）、`4xx` **客户端错**（`400` 语法错、`401` 未登录、`403` 无权限、`404` 找不到、`429` 限流）、`5xx` **服务端崩**（`500` 内部异常、`502` 网关收到坏响应、`503` 过载、`504` 后端超时）。
- **分界符**：HTTP/1.1 长连接复用同一条 TCP 流水管时，靠 `Content-Length`（定长）或 `Transfer-Encoding: chunked`（分段长度+`0\r\n\r\n` 结尾）切分相邻请求/响应。

## 四、HTTP/1.1 队头阻塞 vs HTTP/2 多路复用与 HPACK（NET-44）

HTTP/1.1 虽然有 Keep-Alive，但在同一条 TCP 连接里**必须前一个请求响应完全回来，才能处理下一个**（应用层队头阻塞），导致浏览器被迫对同一个域名并发开 6 条 TCP 连接！

**HTTP/2 三大进化**：
1. **二进制分帧与多路复用（Multiplexing）**：同一条 TCP 连接里拆成多个带 `Stream ID` 的并发数据流，JS、CSS、图片小帧**交错混着发、按 Stream ID 重组**，彻底消灭应用层阻塞（仅需 1 条 TCP 连接！）。
2. **HPACK 头部压缩**：把动辄几百字节重复出现的 `Cookie`/`User-Agent` 建动态字典表，后续请求只发 1 字节索引号！
3. **服务端推送**（实践较少用）与流优先级。

## 五、HTTP/3 与 QUIC：告别 TCP 队头阻塞（NET-45）

HTTP/2 仍坐在 TCP 上——一旦网线丢了 **1 个 TCP 包**，内核为了保证严格字节序，会把整条连接上正在传输的 **所有 Stream 全卡住等那 1 个包重传**！
**HTTP/3 直接放弃 TCP，改跑在基于 UDP 的 QUIC 协议上**：
- 每个 Stream 在 QUIC 里**真正彼此独立**，Stream 1 丢包只卡 Stream 1，Stream 2 照飞不误；
- 把传输层握手和 TLS 1.3 加密握手合并：老用户实现 **0-RTT 零往返瞬间发请求**；
- 引入 **Connection ID**：手机从家里 Wi-Fi 走出电梯切到 5G，IP 变了但 Connection ID 没变，视频会议与下载不断线！

## 六、WebSocket 双向全双工与 gRPC/Protobuf（NET-46）

- **WebSocket**：浏览器端靠一次普通的 HTTP `Upgrade: websocket`（返回 `101 Switching Protocols`）把连接瞬间变成长寿的双向全双工通道，服务端随时主动向前端推行情/弹幕。
- **gRPC**：微服务内部通信王者——底层走 **HTTP/2 多路复用** + **Protobuf 紧凑二进制序列化**（强 Schema、生成 C++/Go/Rust 跨语言代码、体积比 JSON 小数倍），天然支持流式 RPC 与截断超时传递。

## 七、现代密码学三块积木（NET-47）

| 密码学原语 | 解决什么问题？ | 常见算法 | 速度量级 |
| --- | --- | --- | --- |
| **对称加密** | 加解密用同一把密钥，负责**真正加密通信正文** | AES-GCM、ChaCha20-Poly1305 | 极快（硬件指令数 GB/s） |
| **非对称加密 / 密钥协商** | 公钥加密/私钥解密，用来**在不安全网络里安全碰头交换出临时对称密钥** | **ECDHE**（前向保密核心）、RSA | 慢几百倍（只跑在握手阶段） |
| **密码学哈希与数字签名** | 生成不可逆唯一指纹防篡改 + 用私钥签名确认“真是作者本人发出的” | SHA-256、Ed25519 / ECDSA | 极快 |

## 八、数字证书与 CA 信任链（NET-48）

问题：如果黑客在咖啡馆截胡你跟银行建立连接前发来的“银行公钥”，换成黑客自己的假公钥怎么办（**中间人攻击 MITM**）？
解法：**数字证书 = 银行域名 + 银行公钥 + 权威公证处（CA）用 CA 私钥签发的防伪印章！**
你的电脑/操作系统出厂时就预先在本地写死了全球几十家顶级 **根 CA（Root CA）** 的公钥。连上 HTTPS 网站时，服务器递过来一条证书链（`网站证书 -> 中间 CA -> 根 CA`），浏览器用本地预装的根 CA 公钥一层层验印章：
- 如果签名对得上、没过期、且证书里的域名（SAN）刚好匹配网址，才放行；
- 一旦自签名、域名错或系统时间错，浏览器立刻弹出全屏红警告阻断！

## 九、TLS 1.2 vs TLS 1.3 握手全流程（NET-49）

- **TLS 1.2** 需要 **2-RTT** 才能开始发加密 HTTP 数据，且仍遗留过时的静态 RSA（无前向保密）和繁琐加密套件选择。
- **TLS 1.3** 彻底砍掉老旧不安全算法，客户端第一轮 `ClientHello` 就直接**猜好对方大概率支持的椭圆曲线并把自己的 ECDHE 临时公钥一起捎过去**，服务端回完 `ServerHello + 证书签名 + Finished` 只需 **1-RTT** 即可双向收发加密 HTTP！并且强制使用 **ECDHE 临时密钥交换（前向保密 PFS）**：哪怕黑客今天偷录了你全部加密流量、十年后又偷到了服务器长期私钥，也**永远解不开当年那一次通话**！

## 十、常见网络攻防与四层/七层负载均衡（NET-50）

| 安全或架构场景 | 核心原理与应对 |
| --- | --- |
| **ARP 欺骗 / DNS 劫持** | 伪造网关 MAC 或篡改本地 DNS 返回假 IP；开启 HTTPS + 证书校验让任何中间篡改直接暴露报错 |
| **XSS vs CSRF** | XSS 是注入恶意 JS 脚本偷 Cookie；CSRF 是诱导已登录用户点钓鱼页面借用浏览器自动带 Cookie 发请求。应对：`HttpOnly`/`SameSite` Cookie + CSRF Token + 严格输入转义 |
| **四层负载均衡（LVS / IPVS）** | 只看 IP + 端口直接做内核态报文转发（DR/NAT），不拆 TCP/HTTP 内容，性能极高（百万并发入口） |
| **七层负载均衡（Nginx / Envoy）** | 拆开 HTTP/gRPC 看 URL 路径、Header、Cookie 路由，顺便终结 HTTPS、做限流熔断与灰度发布 |

## 十一、微练习与自检

1. 为什么在 TLS 1.3 握手完成后，通信正文依然用 AES/ChaCha20 对称加密而不是继续全用 RSA/ECDH 非对称加密？
2. 某电商接口创建订单用 `POST /orders`，手机在地铁里信号不好超时重试了 1 次导致下了两笔单，这说明缺少了 HTTP 方法之外的什么设计？
3. 四层负载均衡（L4）和七层负载均衡（L7）如果要根据 URL `/api/v2/` 分发给不同微服务集群，必须用哪一种？

<details>
<summary>核对答案</summary>

1. 对称加密（如 AES-GCM 配合 CPU AES-NI 指令集）加解密吞吐可达每秒数 GB，比非对称加密快几个数量级。非对称密码只用于在握手阶段验证身份与协商临时会话密钥。
2. `POST` 天生不是幂等操作，必须让客户端在请求中携带全局唯一的**幂等键（Idempotency-Key / 请求 UUID）**，服务端去重拦截重复提交。
3. 必须用 **七层负载均衡（L7）**（如 Nginx/Envoy），因为四层只看到五元组 IP 与端口，看不见 TCP 流里面的 HTTP URI `/api/v2/`。

</details>
