## 本篇总览（NET-01 ~ NET-08）

写单机程序时，数据只在本机内存和硬盘里打转。一旦要做联机游戏、聊天工具、微服务或者 `LogScan v3` 远程日志收集器，就必须让不同进程隔空对话。本篇参考经典入门教材 *Beej's Guide to Network Programming*，从零基础生活比喻出发，把网络世界的 8 块最底层基石一次讲透。

## 一、网络要解决什么问题？电路交换 vs 分组交换（NET-01）

想让两台相距一千公里的电脑说话，有两种铺线思路：
1. **电路交换（老式电话交换机）**：通话前先在沿途所有交换机拉一条**专属独享专线**，直到挂断才释放。哪怕两个人沉默不说话，这根线也空占着不让别人用。
2. **分组交换（现代互联网的核心）**：把一大段话切成一个个**带收件人地址的小包裹（数据包 / Packet）**，所有人的包裹共用同一根光纤高速混流转发，路由器看包裹上的地址一跳一跳往目的地接力。
   - **好处**：线路利用率极高，某条海底光缆断了也能自动绕路。
   - **代价**：可能出现**排队拥堵（延迟变高）、丢包、或者后发的包裹走近路先到（乱序）**——后面的 TCP 协议就是为了在不可靠的包裹网之上变出可靠体验而生的！

## 二、TCP/IP 五层与 OSI 七层模型及封装过程（NET-02）

为什么不把“找哪台电脑、用网线还是 Wi-Fi、丢包怎么重发、网页 HTML 怎么写”全揉成一个软件？因为那样只要换个 Wi-Fi 网卡，微信和浏览器就得全重写！**分层**让每一层只管自己门口那一小段事，用标准信封一层套一层打包发送（封装），到达对面后再由下往上逐层拆信封（解封装）：

```text
应用层:  [ HTTP GET / HTTP/1.1 或 4B长度头+"INFO ready" ]     ← 写信内容（进程看懂的语言）
               ↓ 套上 传输层 信封
传输层:  [ SrcPort:54322 | DstPort:9090 | SEQ/ACK ] [ 应用数据 ] ← 端口定位“哪一个程序”
               ↓ 套上 网络层 信封
网络层:  [ SrcIP:192.168.1.5 | DstIP:1.2.3.4 | TTL ] [ TCP段 ]   ← IP 定位“地球上哪一台主机”
               ↓ 套上 链路层 信封
链路层:  [ 源MAC | 下一跳路由器MAC | 类型 ] [ IP包 ] [ FCS校验 ] ← MAC 负责“当前局域网下一跳”
               ↓ 物理层：电信号 / 光脉冲 / 无线电波发往网线或空气！
```

| OSI 七层 | TCP/IP 五层（工程最常用） | 核心职责 | 典型协议 / 设备 |
| --- | --- | --- | --- |
| 应用层 / 表示层 / 会话层 | **应用层** | 规定业务报文怎么组织与解读 | HTTP、DNS、SSH、TLS、Protobuf |
| 传输层 | **传输层** | 端到端进程寻址（端口）、可靠重传或尽最大努力交付 | **TCP**、**UDP** |
| 网络层 | **网络层** | 跨网络寻址与路由转发（IP 分组一跳跳接力） | **IPv4**、**IPv6**、ICMP、路由器 |
| 数据链路层 | **数据链路层** | 相邻两个直接相连设备之间传递数据帧 | 以太网 Ethernet、Wi-Fi、MAC、交换机 |
| 物理层 | **物理层** | 传输比特流 `0/1`（电压、光强、射频） | 网线、光纤、集线器 |

## 三、带宽、延迟（RTT）、抖动与丢包率（NET-03）

打游戏觉得“卡”和下载电影觉得“慢”，往往是两个完全不同的指标出了问题：

| 指标 | 生活类比 | 决定什么体验？ | 常见量级参考 |
| --- | --- | --- | --- |
| **带宽（Bandwidth）** | 高速公路有几条车道（每秒最多能挤过去多少比特 `Mbps`/`Gbps`） | 决定下载 4GB 游戏安装包快不快（吞吐量上限） | 百兆/千兆宽带（100 Mbps ≈ 12.5 MB/s） |
| **延迟 / RTT（Round-Trip Time）** | 从你家寄一封信到对方再寄回来的往返跑腿时间（`ms`） | 决定点技能反应快不快、HTTP 握手卡不卡（物理光速硬约束，没法靠加钱加宽带突破！） | 同机回环 `< 0.1 ms`；同城 `5 ms`；跨洋 `150 ms` |
| **抖动（Jitter）** | 有的包裹 20 ms 到、下一个突然 180 ms 才到（延迟的波动程度） | 语音通话一卡一顿、实时竞技人物瞬移 | 良好网络 `< 5 ms` |
| **丢包率（Packet Loss）** | 路上寄丢了百分之几的包裹 | TCP 下即便只有 **1%~2% 丢包**也会疯狂触发降速重传，网页转圈半天打不开 | 有线局域网 `≈ 0%`；劣质 Wi-Fi `> 1%` |

## 四、IP 地址（`127.0.0.1` vs `0.0.0.0`）与端口号（NET-04）

| 黑话 | 生活比喻 | 一句话说清本质 |
| --- | --- | --- |
| **IP 地址**（如 `192.168.1.10`） | **大楼街道门牌号** | 用来唯一定位“互联网上哪一台电脑/哪张网卡” |
| **端口号 Port**（`0 ~ 65535`） | **大楼里的几零几房间号** | 同一台电脑同时开着浏览器、SSH 和你的服务器，操作系统靠目标端口判断包交给哪个进程 |
| **回环地址 `127.0.0.1` (`::1`)** | **自己寄给自己的内部信箱** | 数据由内核直接走虚拟网卡 `lo` 拐回来，**不走网线**，外机连不上，最适合本机测试 |
| **通配地址 `0.0.0.0` (`::`)** | **前台总机接所有门来信** | 服务端绑 `0.0.0.0:9090` 表示监听本机所有网卡 IP（包括 `127.0.0.1` 与局域网 IP） |

> **端口分工规律**：`0 ~ 1023` 是系统知名端口（如 HTTP `80`、HTTPS `443`、SSH `22`、DNS `53`），Linux 下绑定它们通常需要 root 权限；`1024 ~ 49151` 常见服务注册端口（如 MySQL `3306`、Redis `6379`）；`32768 ~ 60999` 留给客户端主动发起连接时系统临时随机挑一个用（**临时端口 Ephemeral Port**）。

## 五、MAC 地址、ARP 地址解析与局域网第一跳（NET-05）

疑惑：既然通信双方都有 IP 地址了，为什么网卡出厂还要烧录一个全球唯一的 48 位十六进制 **MAC 地址**（如 `00:1A:2B:3C:4D:5E`）？
- **IP 地址像通讯地址（会随你搬家/换 Wi-Fi 变）**，决定最终去哪；
- **MAC 地址像身份证号（烧在网卡里）**，只负责在**当前这一跳局域网**内认出“门口那台路由器或邻居电脑的网卡是哪一块”。
- 当你的电脑只知道目标（或者默认网关路由器）的 **IP**、不知道它的 **MAC** 时，会向整个局域网大吼一声 **ARP 广播**（`Who has 192.168.1.1? Tell 192.168.1.5`），拥有那个 IP 的机器会单播回一句 `is at aa:bb:cc:dd:ee:ff`，双方记入本地 ARP 缓存表（Linux 用 `ip neigh` 查看）几分钟后再也不必广播。

> 包跨出你家路由器去公网的路上，**源/目的 IP 几乎始终不变，而源/目的 MAC 每经过一个路由器就会全部换成下一跳的 MAC！**

## 六、打电话（TCP）vs 寄明信片（UDP）（NET-06）

| 对比维度 | **TCP（打电话）** | **UDP（寄明信片）** |
| --- | --- | --- |
| **要不要先接通？** | **要**！必须先三次握手确认双方听筒话筒都好使 | **不用**！填好收件人 IP+端口直接扔进邮筒 |
| **可靠性保证** | 内核提供确认 ACK、超时重传、按序号重排、流量与拥塞控制 | **尽最大努力交付**：丢了不管，后发的还可能先到 |
| **消息边界（极重要！）** | **无边界字节流！** 像一根连续流水管 | **有明确报文边界！** 一次 `sendto` 对应对端一次 `recvfrom` 完整一封 |
| **开销与实时性** | 首部 ≥ 20 字节，丢失重传会卡住后面数据（队头阻塞） | 首部仅 **8 字节**，零握手零重传，延迟极低 |
| **典型用途** | 网页 HTTP/HTTPS、SSH、数据库连接、文件下载、日志收集 | DNS 查询、视频会议、游戏实时位置同步、HTTP/3 QUIC |

## 七、为什么新手写 TCP 一定会遇到“粘包”与“半包”？（NET-07）

因为 **TCP 是一根水管，不是一个个快递盒！**
假设客户端连续调用两次写入：
- 第 1 次：`send("INFO ready")`
- 第 2 次：`send("ERROR timeout")`

由于发送端网卡缓冲合批，或服务端忙了一下晚了一点才来调用 `recv()`，从水桶里一勺舀出来的数据完全可能是：
- **粘包**：`"INFO readyERROR timeout"`（两条消息粘成了一整块！）
- **半包**：`"INFO rea"`（第一条只流了一半，剩下半截还在路上！）

### 怎么彻底治好粘包与半包？
**自己动手在应用层给每条消息套快递盒**——三大经典定界法：
1. **固定长度（Fixed Length）**：规定每条消息固定 64 字节（简单但浪费带宽）。
2. **特殊分隔符（Delimiter）**：每条结尾加 `\n`（文本协议如 Redis RESP、HTTP 头常用；前提是正文不能含原样 `\n`，否则需转义）。
3. **长度前缀（Length-Prefix Frame，工业二进制协议黄金标准）**：每条正文的**最前面固定贴 4 个字节大端整数**写明后面正文有多少字节：

```text
[长度=10 (4字节)] "INFO ready"  [长度=13 (4字节)] "ERROR timeout"
```

这样接收方哪怕一次只收到 3 个字节（连长度头都没凑齐），就先留在 `recv_buf` 等下一次；凑够 `4 + length` 个字节，立刻精准切出一整条消息！

## 八、C/S 与 P2P 架构、Socket 直觉及 `nc` 零代码对话体验（NET-08）

- **C/S（Client-Server）**：客户端永远处于主动拨号方，服务端 24 小时守着固定端口等待连接（几乎所有网站与后端微服务的模型）。
- **P2P（Peer-to-Peer）**：每个节点既是客户端也是服务端，彼此直接交换分片（BT 下载、WebRTC 音视频）。
- **Socket（套接字）是什么？** 对 C++ 程序员来说，Socket 根本不是玄学——它只是操作系统分发给你的**一个普通整数号牌（文件描述符 `fd`）**。写进这个号牌的数据，内核协议栈会自动套上 TCP/IP/MAC 信封丢出网卡！

### 2 分钟破冰体验（用 Linux `nc` 亲眼看见回环 TCP 通信）

```bash
# 终端 1（当服务端：站在本机 9090 房间门口监听）
nc -l -p 9090

# 终端 2（当客户端：拨号连向本机 127.0.0.1 的 9090 房间）
nc 127.0.0.1 9090
```

连上后在终端 2 输入 `INFO hello` 回车，终端 1 立刻原样打印 `INFO hello`。这就是最真实的 TCP Socket 全过程！

## 九、微练习与自检

1. 把网速从 100 Mbps 升级到 1000 Mbps 后，打北京连接美国西海岸服务器的网络游戏 ping 值（RTT ~160 ms）会变成 16 ms 吗？为什么？
2. 本机调试服务端绑 `127.0.0.1:9090`，局域网同事的电脑为什么一直报 `Connection refused`？
3. 客户端 `send("A")` 再 `send("B")`，为什么服务端一次 `recv()` 可能直接拿到 `"AB"`？

<details>
<summary>核对答案</summary>

1. **不会！** 1000 Mbps 提高的是“马路有多宽（带宽/吞吐量）”，而 RTT 160 ms 取决于光信号在跨洋光纤中往返一趟的物理时间与沿途路由器转发时间（延迟），加宽车道并不会让单辆车跑得比光速更快。
2. `127.0.0.1` 是仅限本机内部回环网卡 `lo` 的地址，外机数据包进不来。改成绑定 `0.0.0.0:9090` 才会监听本机所有网卡。
3. TCP 是无边界字节流，内核发送缓冲区可能合批发送，接收缓冲区也可能一次性积攒两次到达的数据再被 `recv()` 读走。

</details>
