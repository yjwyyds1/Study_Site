## 本篇总览（NET-19 ~ NET-30）

如果说 IP 层只是“尽可能把信扔向远方”，那么**传输层**才是真正决定“服务高并发下卡不卡顿、连接断不断得干净、端口会不会瞬间占满爆掉”的主战场。本篇逐节打通传输层全部核心机制（`NET-19` ~ `NET-30`）。

---

## 一、UDP 极简首部与可靠 UDP 思路（NET-19）

```text
 0                   1                   2                   3
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
|          源端口号 (16位)      |         目的端口号 (16位)     |
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
|          UDP 长度 (16位)      |        UDP 校验和 (16位)      |
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
|                      应用层数据报文 ...                         |
```

UDP 首部只有区区 **8 个字节**（源端口、目的端口、长度、校验和）。没有连接、没有序列号、没有重传与拥塞控制——收发极快但全靠自己兜底。
**为什么游戏/音视频/HTTP3 反而基于 UDP 自己造轮子（如 QUIC、KCP）？**
- 因为内核写死的 TCP 升级极其困难（需要全地球 OS 内核升级），而把顺序确认、FEC 前向纠错、多路复用搬到**用户态的 UDP 之上**，既能避免 TCP 丢一个包就卡死整条流的“队头阻塞”，还能实现 0-RTT 秒连和 Wi-Fi 切 4G 不断线！

## 二、TCP 20 字节首部与六大核心标志位（NET-20）

```text
TCP 首部 (无选项最短 20 字节):
  [ 源端口 (16) | 目的端口 (16) ]
  [            序列号 Sequence Number (32)             ]  ← 当前包第1个字节的编号
  [          确认号 Acknowledgment Number (32)         ]  ← 期望对方下次发来的下一个字节号！
  [首部长|保留| URG | ACK | PSH | RST | SYN | FIN | 窗口大小 rwnd ]
  [        校验和 (16)        |       紧急指针 (16)    ]
```

记住其中最关键的 **5 个控制开关标志位（Flags）**：
1. **`SYN`（Synchronize）**：请求建立连接，携带初始序列号 ISN（占 1 个逻辑字节序号）。
2. **`ACK`（Acknowledgment）**：确认号字段生效，表示“在此编号之前的所有字节我都安全收到啦”。
3. **`FIN`（Finish）**：我这边数据发完了，请求关闭我的发送方向（仍可收你发来的剩余数据）。
4. **`RST`（Reset）**：**暴力异常中断**！端口没进程在监听、连接半途崩溃重启、或收到莫名报文时直接甩一张 `RST` 撕毁连接（客户端常看到 `Connection reset by peer`）。
5. **`PSH`（Push）**：提醒接收方内核尽快把缓冲区里的数据推给用户程序 `recv()`，别攒着。

## 三、TCP 三次握手深潜与 SYN Flood 防护（NET-21）

```text
客户端                                    服务端 (LISTEN)
  │ ─── SYN=1, seq=x ───────────────────► │  进入 SYN_RCVD（放入半连接队列）
  │ ◄── SYN=1, ACK=1, seq=y, ack=x+1 ──── │
  │ ─── ACK=1, seq=x+1, ack=y+1 ────────► │  进入 ESTABLISHED（移入全连接 accept 队列）
```

### 1. 为什么非得“三次”握手，两次行不行？
- **确认双方的收发能力都正常**：第 1 次证明“客能发、服能收”；第 2 次证明“服能发、客能收”；第 3 次证明“客接收正常并知晓服务端的序列号”。如果是两次，服务端刚发完 `SYN+ACK` 就开好内存等，万一包丢了或者这是历史网络里绕回来的迟到旧 `SYN`，服务端就傻等浪费资源了！
- **同步初始序列号（ISN）**：双方各自通过时钟+随机算法选一个不撞车的起始号码 `x` 和 `y`（绝不是从 0 开始！防止旧连接幽灵数据包伪造或注入）。

### 2. SYN Flood 攻击与 SYN Cookies
攻击者伪造一万个假源 IP 疯狂发 `SYN` 却永远不回第三次 `ACK`，迅速塞爆服务端的半连接队列（`syn backlog`）导致正常用户连不上。开启 **`tcp_syncookies`** 后，服务端收到 `SYN` 时先**不分配任何队列内存**，而是把五元组与时间戳用加密哈希算出一个数字当作 `seq=y` 发回去——如果对方是真客户，第三次握手的 `ack = y + 1` 能反算验证通过再当场建连！

## 四、TCP 四次挥手与 11 个状态机流转（NET-22）

```text
主动关闭方 (如客户端)                     被动关闭方 (如服务端)
  │ ─── FIN=1, seq=u ───────────────────► │
  │     [FIN_WAIT_1]                      │  进入 [CLOSE_WAIT]（此时服务端还能把没发完的包发完！）
  │ ◄── ACK=1, ack=u+1 ────────────────── │
  │     [FIN_WAIT_2]                      │  应用调 close(fd) 后才发 FIN
  │ ◄── FIN=1, ACK=1, seq=w, ack=u+1 ──── │  进入 [LAST_ACK]
  │ ─── ACK=1, seq=u+1, ack=w+1 ────────► │  收到即变为 [CLOSED]
  │     [TIME_WAIT] (等 2MSL 后才 CLOSED) │
```

### 为什么建立连接三次，断开要四次？
因为 TCP 是**全双工**的！主动方发 `FIN` 只代表“**我不给你发了，但你还能继续给我发**”；被动方往往不能立刻关，只能先回 `ACK` 告诉对方“知道你不发了，等我把手头最后半页响应数据发给你再挂断”，所以 `ACK` 和被动方的 `FIN` 拆成两趟发送！

> **线上高频故障点：`CLOSE_WAIT` 堆积成千上万！**
> 只要用 `ss -tan` 看到大量连接卡死在 **`CLOSE_WAIT`**，**100% 是你服务端自己的代码 BUG**——对端已经关了连接并触发了你的 `recv() == 0`，但你的程序忘了调用 `close(fd)`！

## 五、`TIME_WAIT`（2MSL）与 `SO_REUSEADDR`（NET-23）

**主动关闭连接的那一方**在发出最后一个 `ACK` 后，必须强制在 **`TIME_WAIT` 状态停留 2 倍 MSL（Maximum Segment Lifetime，Linux 固定为 60 秒）** 才彻底销毁控制块。

### 为什么必须忍痛等这 60 秒？两大硬理由：
1. **防止最后发出的 `ACK` 在路上丢了**：万一那个 `ACK` 丢了，被动方会重传 `FIN`，主动方留在 `TIME_WAIT` 才能补发 `ACK` 让对方安详关闭；
2. **让本次连接在网线里迷路的残留旧包彻底老死**：如果 1 秒后用同一对 IP+端口立刻重连，老连接滞留网络的旧数据包可能会混进新连接串台！

### 开发重启服务端报 `Address already in use` 怎么办？
因为刚刚主动断开重启时旧监听连接留在了 `TIME_WAIT`，只需在服务端 `bind()` 之前加上：
`int opt = 1; setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));`
如果是**短连接客户端**高并发狂压，千万不要由服务端主动 `close`，否则服务端积压百万 `TIME_WAIT` 耗尽内存和临时端口；通常让**客户端主动断开**或使用 **HTTP Keep-Alive 长连接复用**！

## 六、可靠传输底座：ARQ、回退 N 帧（GBN）与选择重传（SACK）（NET-24）

- **停等协议（Stop-and-Wait）**：发 1 个包，死等对面回 ACK 再发第 2 个。如果跨洋 RTT 150ms，一次只发 1.4KB，吞吐只有可怜的 `9 KB/s`，完全跑不满光纤！
- **流水线并发（Pipelining）**：允许一口气连续发出一个窗口的多个分段。万一中间第 3 号包丢了：
  - **GBN（回退 N 帧）**：如果只支持累计确认（`ACK=3` 表示 1、2 到了，3 还没到），那后面已经安全到达的 4、5、6 都得连坐一起重传，极度浪费。
  - **SACK（选择性确认，现代 TCP 默认开启）**：接收方在 TCP 选项里精准上报“3 丢了，但 4~8 我已经帮你先收着了”，发送方只需**精准重传第 3 号包**，效率暴涨！

## 七、滑动窗口与流量控制（`rwnd`）（NET-25）

发送方发太快、接收方应用没来得及调用 `recv()` 取走把内核接收缓冲区塞爆怎么办？
- 接收方在每次返回的 `ACK` 首部里自带一个 **16 位接收窗口大小 `rwnd`（Receive Window）**，直白喊话：“我缓冲区还剩 32KB 空位，你最多只能再往外发 32KB！”
- 当 `rwnd` 降到 **`0`** 时，发送方立刻刹车暂停发新包，并开启**零窗口探测定时器**（每隔几秒发 1 字节小包问一声“空出来没有？”），避免对面发出的“窗口恢复通知包”万一丢了导致死锁！
- （注意：单靠 16 位最大只能写 `65535B = 64KB`，千兆网络下完全不够用！现代 TCP 握手时会协商 **Window Scale 窗口缩放因子**，把实际窗口放大到几 MB 甚至几十 MB）。

## 八、超时重传（RTO）与快速重传（NET-26）

1. **RTO（Retransmission Timeout）动态计算**：死等 1 秒太久、等 5ms 又误判，TCP 靠不断采样实时 RTT 的**平滑均值 `SRTT` 和抖动方差 `RTTVAR`**（Jacobson/Karels 算法）动态算出最贴合当前网速的超时时间；如果连续重传仍失败，RTO 会**指数退避**（1s -> 2s -> 4s -> 8s）以免雪崩。
2. **快速重传（Fast Retransmit）——不等定时器熬完！**：发送方发了 `1, 2, 3, 4, 5`，其中 `2` 丢了，对端每收到 `3, 4, 5` 就会因为 `2` 缺失而连续回发三次 **`ACK=2`**（总共 3 次冗余 ACK）。发送方一看不用傻等 RTO 超时，当场立刻把 `2` 重发过去！

## 九、拥塞控制（`cwnd`）：慢启动、拥塞避免、Cubic 与 BBR（NET-27）

流量控制（`rwnd`）怕把**接收端**淹死，**拥塞控制（`cwnd`）**怕把**公网中间的路由器**堵死！真正允许在途的字节数 = **`min(cwnd, rwnd)`**。

1. **慢启动（Slow Start）**：刚连上不知道路有多宽，`cwnd` 从小（如 10 MSS）起步，每收到 1 个 ACK 翻倍**指数增长**（`10 -> 20 -> 40 -> 80`），直到触碰慢启动阈值 `ssthresh`。
2. **拥塞避免（Congestion Avoidance）**：过了阈值改成每轮 RTT 只 `+1 MSS` 线性试探路宽。
3. **发生丢包怎么减产？**
   - 超时重传（说明路彻底堵死了！）：`ssthresh = cwnd / 2`，`cwnd` 狠砍回 **`1`** 重新慢启动；
   - 收到 3 次冗余 ACK（快重传，只是轻微丢包）：进入**快恢复**，`cwnd` 砍半后直接接着线性增长（现代 Linux 默认算法 **Cubic** 采用三次函数曲线更平滑地冲顶）。
4. **Google BBR 的范式革命**：传统 Cubic 等着“把路由器缓存队列全塞满直到溢出丢包”才知道快慢（引发高延迟 Bufferbloat）；**BBR 不靠丢包猜拥塞**，而是主动测算链路的真实**瓶颈带宽 `BtlBw` 与最小无拥塞延迟 `RTprop`**，踩在刚好塞满带宽又零排队的黄金点上飞奔，高丢包跨国网络速度常快数倍！

## 十、Nagle 算法、延迟确认与 40ms 卡顿陷阱（NET-28）

- **Nagle 算法**：为了防止 Telnet 敲键盘每按 1 个字母就发 41 字节大包裹浪费宽带，规则规定：**只要前面发出去的包还有没收到 ACK 的，手里攒着不足一个 MSS 的零碎小包就先别发**。
- **延迟确认（Delayed ACK）**：接收方收到数据后忍住不立刻回裸 ACK，先等 40ms（Linux）看看自己应用是不是马上要回响应数据，好顺便“捎带确认”省一个包。
- **致命碰撞！** 如果客户端开启了 Nagle、分两次小 `write` 发请求头和正文，服务端又开了延迟确认死等凑完整请求——**客户端等服务端的 ACK 才发第 2 块，服务端等客户端发第 2 块才凑齐回响应，平白无故每次请求卡死 40ms！**
- **工程铁律**：高实时性 RPC / 游戏 / `LogScan` 服务端与客户端几乎一律设置 **`setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &on, sizeof(on))`** 禁用 Nagle，并在应用层用缓冲区一次性攒好整帧再 `send`！

## 十一、TCP Keepalive 内核保活 vs 应用层心跳（NET-29）

如果客户端电脑突然直接拔电源或网线断了，由于没机会发 `FIN`/`RST`，服务端永远傻等在 `ESTABLISHED`！
- **内核 TCP Keepalive**：默认长达 **2 小时**无数据才发探测包，而且只能探通内核协议栈活着，探测不到“进程其实已经死锁卡死”！
- **应用层心跳（Heartbeat）**：在业务帧里每隔 `10~30` 秒发一条轻量的 `PING`/`PONG` 帧。既能在秒级踢掉死连接释放内存，又能穿透各种怪异的中间 NAT/防火墙保住长连接映射不被掐掉！

## 十二、半关闭 `shutdown`、`RST` 复位与 `SIGPIPE` 杀进程陷阱（NET-30）

- **`close(fd)` vs `shutdown(fd, SHUT_WR)`**：
  - `close()` 会减少文件描述符引用计数并彻底关闭读写（若其他线程还在用该 fd 则只减计数不发 `FIN`）。
  - `shutdown(fd, SHUT_WR)` **不销毁 fd**，而是优雅发送 `FIN` 声明“客户端全发完了，但还等着把服务端最后几行响应读到 EOF”——非常适合短请求一次性交互！
- **往已断开的 Socket 写两次触发 `SIGPIPE`**：
  对端早已断开并给你回过一次 **`RST`**；如果你的服务端忘了检查直接继续对这个连接调 `write`/`send`，Linux 内核会直接向你的进程甩出 **`SIGPIPE` 信号——默认动作是当场杀死整个服务端进程（退出码 141）！**
  > 写任何 Linux 网络服务端，`main()` 第一行必定加：**`std::signal(SIGPIPE, SIG_IGN);`**（忽略该信号，让 `send()` 安全返回 `-1` 并设置 `errno == EPIPE`，只踢掉这一条坏连接而不拖累全服崩溃！）。

## 十三、微练习与自检

1. 为什么在服务端用 `ss -tan` 观察到大量连接停留在 `CLOSE_WAIT` 时，重启服务器往往只是临时缓解，根本原因在自己代码里？
2. 某 HTTP/RPC 服务平均一次请求只需 2 ms，但压测发现大量请求固定在 42 ms 左右才返回，排查思路应该先怀疑哪两个参数撞车？
3. 为什么写跨公网的高吞吐服务，开启 `SO_REUSEADDR` 和 `std::signal(SIGPIPE, SIG_IGN)` 几乎是服务端 `main` 函数的起手标配？

<details>
<summary>核对答案</summary>

1. `CLOSE_WAIT` 表示对端已经发 `FIN` 请求断开，内核等待**本机应用程序调用 `close(fd)`** 发自己的 `FIN`。大量 `CLOSE_WAIT` 意味着业务层出现文件描述符泄漏（忘了关闭 socket）。
2. 极大概率是 **Nagle 算法（发送方小包等待前 ACK）+ TCP 延迟确认（接收方憋着 40ms 才回 ACK）** 撞车！客户端分两次小 `send` 发送请求头和体且没设 `TCP_NODELAY`，必卡 40ms。
3. `SO_REUSEADDR` 解决服务端主动重启时旧监听端口停留在 `TIME_WAIT` 导致 `bind` 报 `Address already in use`；`SIG_IGN` 屏蔽 `SIGPIPE` 防止单个客户端异常断连发 `RST` 后把整个服务进程误杀。

</details>
