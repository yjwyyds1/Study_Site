## 本篇只解决这 1 类问题

单机写几条 SQL 很容易。但真实系统要同时面对三座大山：
1. **几千个并发连接同时改同一批账户/库存数据**，怎么做到既不互相覆盖丢更新，又不一把大锁把所有读请求卡死？
2. **服务器突然断电或 `kill -9`**，内存里改了一半还没刷盘的脏页、和刷了一半的事务怎么在重启后自动缝合干净？
3. **单台数据库扛不住 TB 级数据或挂机了**，怎么做主从高可用、水平分片、以及跨微服务的分布式事务？

本篇完整覆盖课程 `DB-40` ~ `DB-50`，带你贯通单机事务内核（锁、MVCC、ARIES 恢复）与分布式存储架构（复制、分片、2PC 与 Saga）。

## 一、ACID 四大特性的工程本质 (DB-40)

人们常把 ACID 当八股文背，但在数据库内核里，四个字母分别由完全不同的子系统兜底：

| 特性 | 一句话工程本质 | 内核主要实现机制 |
| --- | --- | --- |
| **A（Atomicity，原子性）** | 事务是不可分割的最小工作单元：**要么全做，要么全不做** | **Undo Log（回滚日志）**：中途报错或崩溃时，逆向撤销已改写的数据 |
| **C（Consistency，一致性）** | 事务前后，数据库必须从**一个合法业务状态变到另一个合法状态**（如 `A+B=1000`、`balance >= 0`） | **唯一特殊点**：`C` 是**目标**而非单纯的内核机制，由数据库约束（外键/`CHECK`）+ `A`/`I`/`D` + **应用代码逻辑**共同保证 |
| **I（Isolation，隔离性）** | 并发执行的多个事务，彼此的中间未提交状态尽量不可见，避免相互踩踏 | **锁机制（2PL / Gap Lock）+ MVCC 多版本并发控制** |
| **D（Durability，持久性）** | 一旦 `COMMIT` 返回成功，哪怕下一毫秒机器断电，数据也绝不丢失 | **WAL / Redo Log + `fsync()`** 保证重启可前滚恢复 |

## 二、并发下的 6 大数据异常（Anomalies） (DB-41)

假设初始状态：账户 `A = 100`，`B = 100`。没有隔离保护时，并发事务会出现从轻到重 6 种典型灾难：

1. **脏写（Dirty Write）**：T1 把 `A` 改成 `200`，T2 把 `A` 改成 `300` 并提交；随后 T1 回滚把 `A` 恢复成 `100`，把 T2 已提交的 `300` 活活抹掉了！（所有隔离级别都绝对禁止。）
2. **脏读（Dirty Read）**：T1 把 `A` 改成 `200`（未提交）；T2 读到 `A = 200` 并基于它发出发货指令；随后 T1 发生异常 `ROLLBACK` 回滚回 `100`——T2 读到了根本不存在的“幽灵数据”。
3. **不可重复读（Non-Repeatable Read）**：同一个事务 T1 内部，第 1 次读 `A = 100`；期间 T2 把 `A` 改成 `200` 并 `COMMIT`；T1 再次读同一行变成了 `200`（前后两次读**同一行**结果不一致）。
4. **幻读（Phantom Read）**：同一个事务 T1 内部，第 1 次查 `WHERE level = 'ERROR'` 得到 3 行；期间 T2 **新插入** 1 条 `ERROR` 并 `COMMIT`；T1 再执行同一查询变成了 4 行（凭空多出“幻影行”）。
5. **丢失更新（Lost Update）**：经典的读-改-写竞态！T1 和 T2 同时读到余额 `100`，T1 算 `100 - 10 = 90` 写回，T2 算 `100 - 20 = 80` 写回——结果扣了两次钱余额却是 `80` 而不是 `70`！
6. **写偏斜（Write Skew，高阶杀手）**：假设规则要求“值班医生至少保留 1 人”，当前 Alice 和 Bob 都在值班。T1 和 T2 在同一个**快照**里同时看到有 2 人在值班：T1 决定让 Alice 请假（`UPDATE` Alice 行），T2 决定让 Bob 请假（`UPDATE` Bob 行）——**两人修改的根本不是同一行！** 互不冲突双双提交，最终医院 0 人值班！

## 三、SQL 四大隔离级别与主流引擎真实行为 (DB-42)

SQL-92 标准按允许的异常定义了 4 级隔离。**务必注意：现代数据库（MySQL InnoDB / PostgreSQL）基于 MVCC 的实际表现比 SQL-92 纸面标准更强！**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 写偏斜 | 主流数据库默认情况与内核特点 |
| --- | --- | --- | --- | --- | --- |
| **`READ UNCOMMITTED`** | 可能 | 可能 | 可能 | 可能 | 几乎没人用（能读到别人未提交的脏内存） |
| **`READ COMMITTED` (RC)** | **无** | 可能 | 可能 | 可能 | **PostgreSQL / Oracle 默认**：每条 SQL 语句独立拿最新快照 |
| **`REPEATABLE READ` (RR)** | **无** | **无** | 标准允许；**InnoDB/PG 快照读无** | **可能**（Snapshot Isolation） | **MySQL InnoDB 默认**：事务首句拿固定快照；当前读用 Next-Key 锁防幻读 |
| **`SERIALIZABLE`** | **无** | **无** | **无** | **无** | **SQLite 默认全局串行化**；PG 用无锁乐观冲突检测 **SSI**；InnoDB 给普通 `SELECT` 隐式加共享锁 |

## 四、共享锁、排他锁、意向锁与两阶段锁协议（2PL） (DB-43)

把内存并发里的 `std::shared_mutex` 搬到数据库行上，就是读写锁：
- **S 锁（Shared 共享锁 / 读锁）**：多个事务可以同时拿同一行的 S 锁（读读不互斥）。
- **X 锁（Exclusive 排他锁 / 写锁）**：拿了 X 锁期间，其他人既不能拿 X 锁也不能拿 S 锁（读写互斥、写写互斥）。

### 1. 为什么需要意向锁（`IS` / `IX`）？

假设事务 T1 锁住了 1000 万行大表里的第 8888 行（加了行级 `X` 锁）。此时事务 T2 想整张表加表级锁（如 `LOCK TABLES` 或 `ALTER TABLE`）。如果没有意向锁，T2 得把 1000 万行一行行翻遍才能确认表里有没有行锁！
**意向锁（Intention Lock）是挂在表门口的“告示牌”**：
- T1 准备锁某一行之前，**先顺手在表门口挂一块 `IX`（意向排他）或 `IS`（意向共享）牌子**；
- `IS` 和 `IX` **互相完全兼容**（不同事务同时改不同行互不阻塞），但表级 `S`/`X` 锁一看门口挂着 `IX` 牌子，不用翻表就知道里面有人在改行，**$O(1)$ 瞬间阻塞等待**！

### 2. 两阶段锁协议（2PL）与严格 2PL（Strict 2PL）

```text
事务生命周期中的锁数量变化：
  锁数量
   ▲      Growing Phase (加锁阶段)        Shrinking Phase (解锁阶段)
   │     /                        \
   │    /   只准加锁，不准放锁！      \    只准放锁，不准再加新锁！
   │   /                            \
   └──┴──────────────────────────────┴──▶ 时间
                                     ▲
   Strict 2PL（工业界标配）: 把所有 X 锁一直攥到 COMMIT/ROLLBACK 瞬间才统一释放！
```

为什么工业界几乎都用 **Strict 2PL**？因为如果事务中途就提前释放 X 锁，别人读走你的修改并跟着提交了，结果你最后一步报错 `ROLLBACK`，就会引发灾难性的**级联回滚（Cascading Abort）**！

## 五、InnoDB 行锁、间隙锁（Gap Lock）与临键锁（Next-Key Lock） (DB-44)

在 `REPEATABLE READ` 隔离级别下，普通 `SELECT` 走 MVCC 快照；但带锁读（`SELECT ... FOR UPDATE`）以及 `UPDATE` / `DELETE`（叫**当前读 Current Read**）如果只锁住“已经存在的行”，别人依然可以往行与行之间的缝隙里 `INSERT` 新行导致**幻读**！

InnoDB 发明了三种逐级放大的索引锁来彻底堵死缝隙（假设索引里已有记录 `10`、`20`、`30`）：

```text
索引键轴:  (-∞) ────── [ 10 ] ────── [ 20 ] ────── [ 30 ] ────── (+∞)
                        ▲     (10, 20)     ▲
                   Record Lock   Gap Lock
                        └───────┬─────────┘
                         Next-Key Lock = (10, 20]  (左开右闭区间!)
```

1. **Record Lock（记录锁）**：只锁住某一条具体索引记录本身（如精准命中唯一索引 `WHERE id = 20` 时，退化为只锁 `20`）。
2. **Gap Lock（间隙锁）**：锁住两个索引值之间的空隙（如 `(10, 20)`），**不锁记录本身**，专门阻止其他事务往缝隙里 `INSERT`（如插入 `15` 会被阻塞）。注意：**两个事务可以同时持有同一个 Gap 的间隙锁（Gap Lock 之间互相兼容，只阻塞 Insert Intention Lock 插入意向锁）**！
3. **Next-Key Lock（临键锁）**：`Record Lock + Gap Lock` 的组合，默认左开右闭区间 `(10, 20]`。在范围查询 `WHERE id > 15 FOR UPDATE` 时，把 `(10, 20]`、`(20, 30]`、`(30, +∞)` 全部锁死，彻底封杀幻读！

> **生产性能核弹级警示**：InnoDB 的行锁是**加在索引记录上的**！如果你的 `UPDATE logs SET ... WHERE message = 'abc'` 里的 `message` **没有索引**，InnoDB 只能走全表扫聚簇索引，并把**全表所有记录和所有间隙全部锁死**——等效于整张表瘫痪锁表！

## 六、MVCC 多版本并发控制：Undo Log 与 ReadView 原理 (DB-45)

2PL 最大的痛点是“写会阻塞读，读也会阻塞写”。现代数据库（PostgreSQL / MySQL InnoDB / SQLite WAL）靠 **MVCC（Multi-Version Concurrency Control）** 实现**“读不阻塞写、写不阻塞读”**：写者在改写数据时，不直接抹掉旧数据，而是保留历史版本链，让并发读者按自己的“快照视野”各读各的版本！

```text
InnoDB 聚簇索引行版本链（每行带隐藏列 trx_id 与 roll_ptr）：

  [当前最新行: id=1, balance=300 | trx_id=105 | roll_ptr]
                                                    │
                                                    ▼ (指向 Undo Log 历史版本)
  [Undo 旧版本 1: id=1, balance=200 | trx_id=102 | roll_ptr]
                                                    │
                                                    ▼
  [Undo 旧版本 2: id=1, balance=100 | trx_id=90  | roll_ptr=NULL]
```

### ReadView（读视图）的 4 步可见性判定算法

当一个事务启动读快照时，引擎生成一份当前时刻的 **ReadView**，包含 4 个核心字段：
- `m_ids`：生成瞬间**所有还活跃（未提交）的事务 ID 列表**；
- `min_trx_id`：`m_ids` 里的最小值；
- `max_trx_id`：生成瞬间系统下一个即将分配的新事务 ID；
- `creator_trx_id`：我自己的事务 ID。

顺着版本链从最新往最旧逐个比对版本上的 `trx_id`：
1. `trx_id == creator_trx_id`：**是我自己刚改的** $\rightarrow$ **可见！**
2. `trx_id < min_trx_id`：在快照生成前就已经提交完了 $\rightarrow$ **可见！**
3. `trx_id >= max_trx_id`：快照生成之后才开启的未来事务 $\rightarrow$ **不可见！**（顺着 `roll_ptr` 继续找更老版本）
4. `min_trx_id <= trx_id < max_trx_id`：查它是否在 `m_ids` 活跃列表里——**在列表里说明当时还没提交（不可见，继续顺藤摸瓜）；不在说明已经提交了（可见）！**

### `READ COMMITTED` vs `REPEATABLE READ` 的唯一底层代码区别

整个 MVCC 引擎代码几乎一模一样，唯一差别只有一行：
- **`READ COMMITTED`**：在事务里的**每一次 `SELECT` 执行前，都重新生成一个新的 ReadView**（所以能看到别人刚提交的新数据，产生不可重复读）。
- **`REPEATABLE READ`**：仅在事务里**第一次执行 `SELECT` 时生成一次 ReadView**，整个事务后续所有普通 `SELECT` 永远复用这同一张静态照片（天然实现可重复读）！

> **Snapshot Isolation 依然防不住写偏斜（Write Skew）**：因为普通快照读不加锁，两个并发事务各自读同一个快照并修改**互不重叠的两行**时不会触发写写冲突。必须改用 `SELECT ... FOR UPDATE` 强制当前读加锁，或使用 PostgreSQL 的 `SERIALIZABLE`（SSI 序列化快照隔离）。

## 七、乐观锁 vs 悲观锁，以及死锁检测与破局 (DB-46)

### 1. 悲观锁 vs 乐观锁选型

| 策略 | 典型 SQL 写法 | 适用场景 |
| --- | --- | --- |
| **悲观锁（Pessimistic）** | `SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;` | **写冲突极高**（秒杀抢同一件库存、热账号扣款），先抢锁再干活，避免大量无效重试 |
| **乐观锁（Optimistic / CAS）** | `UPDATE accounts SET balance = balance - 10, version = version + 1 WHERE id = 1 AND version = 5;` | **读多写少、冲突罕见**；不加长锁，更新完检查 `affected_rows == 1`；若为 `0` 说明被别人抢先改了，应用层重试 |

> **队列抢单黑科技：`FOR UPDATE SKIP LOCKED`**：多个 Worker 并发从任务表抢任务时，传统 `FOR UPDATE` 会让后来的 Worker 干等锁。加上 **`SKIP LOCKED`**（PG/MySQL 8+ 支持），Worker 直接跳过已经被别人锁住的行，拿下一条空闲任务，吞吐瞬间起飞！

### 2. 死锁（Deadlock）是怎么产生的，如何自动检测和预防？

```text
事务 T1: 锁住行 1 ──────────────────▶ 申请锁行 2 (等待 T2!)
事务 T2: 锁住行 2 ──▶ 申请锁行 1 (等待 T1!)   ◀── 形成等待环 (Cycle)!
```

- **数据库自动检测**：引擎在后台维护一张**等待图（Wait-for Graph）**，一旦发现有向环（或等待超过 `innodb_lock_wait_timeout`），立即挑选回滚代价最小（修改行数最少）的那个事务作为**牺牲品强制 `ROLLBACK` 报错**，让另一个事务顺利继续。
- **工程根治铁律（固定加锁顺序）**：转账 `transfer(from, to, amount)` 时，**永远先锁 ID 较小的账户，再锁 ID 较大的账户**（`first = min(from, to), second = max(from, to)`），从数学上彻底破坏循环等待条件，让死锁概率降为 `0`！

## 八、WAL、Redo/Undo、Checkpoints 与 ARIES 崩溃恢复直觉 (DB-47)

为了性能，数据库绝不会在每次 `UPDATE` 一行时把 16KB 脏页随机刷回磁盘（Buffer Pool 采用 **Steal / No-Force** 策略：允许把未提交事务的脏页提前偷刷到磁盘以腾内存；也不强制提交瞬间刷整个数据页，只强制顺序刷极小的日志）。

这就要求日志必须同时承担两份职责：
- **Redo Log（物理/生理重做日志）**：记录“某个表空间某页偏移处改成了什么字节”。顺序追加写，**`COMMIT` 时必须先 `fsync` 落盘（Write-Ahead Logging 铁律：日志先于数据页落盘）**！每条日志带单调递增序号 **LSN（Log Sequence Number）**。
- **Undo Log（逻辑回滚日志）**：记录“这行改之前是什么样子”，供事务失败回滚与 MVCC 读旧版本使用。
- **Fuzzy Checkpoint（模糊检查点）**：后台悄悄把脏页刷回磁盘，并往日志写一个检查点标记，缩短崩溃重启时需要扫描的历史日志长度。

### ARIES 崩溃恢复三部曲（重启瞬间发生了什么？）

机器突然断电重启后，磁盘上的数据页可能是“新旧混杂的半成品”。ARIES 算法用极其严谨的三遍扫描把数据库拉回 100% 一致状态：

```text
崩溃重启时 WAL 时间线:
  ───[Last Checkpoint]───────[已提交 T1]────[未提交 T2]────[💥 断电!]
          │
          ▼
  1. Analysis (分析阶段) : 从最近 Checkpoint 扫到日志末尾，算出崩溃瞬间的脏页表 (DPT) 与未提交活跃事务表 (Loser Txns = {T2})
  2. Redo     (重做阶段) : 从最早脏页的 recLSN 一路向前“重演历史”（连 T2 的改动也先重放，让所有页恢复到断电前一瞬间的物理状态！）
  3. Undo     (撤销阶段) : 逆序扫描，只把所有未提交的 Loser 事务 (T2) 全部撤销；每撤销一步写一条 CLR（补偿日志记录），保证撤销过程本身再次断电也不会重复撤销死循环！
```

## 九、主从复制、复制延迟与脑裂（Split-Brain） (DB-48)

单机撑不住读流量或需要防单点故障时，引入 **Primary（主库接写） → Replica（从库接只读）** 复制架构，主库把 Binlog / WAL 源源不断流式发给从库重放。

| 复制模式 | 同步时机与性能 | 断电/主库宕机风险 |
| --- | --- | --- |
| **异步复制（Async，默认）** | 主库写完本地 WAL 直接对客户端返回成功，后台慢慢发给从库 | **性能最高**；主库硬盘彻底炸毁切从库时，会丢最后几毫秒已提交数据（RPO > 0） |
| **半同步复制（Semi-Sync）** | 主库至少等 **1 台从库** 收到并写进 Relay Log 返回 ACK 后才算提交成功 | 折中黄金方案：兼顾高可用不丢数据与可接受延迟 |
| **全同步 / 共识复制（Raft/Paxos）** | 多数派（Quorum）节点全部落盘才算成功（如 TiDB / CockroachDB / MySQL Group Replication） | 强一致零丢数据（RPO = 0），跨机房 RTT 延迟较高 |

### 1. 复制延迟引发的“自己写完自己看不见”

用户刚发完一条帖子（写主库），页面刷新立刻发读请求落到从库上——由于主从复制有几十毫秒延迟，从库还没同步到那条数据，用户惊恐地发现“我刚发的帖子没了！”（违反 **Read-Your-Writes**）。
**常见工程解法**：
- 用户刚发生写操作后的几秒窗口期内，把该用户的读请求**强制路由回主库**（写后读粘性路由）；
- 或读请求携带主库提交返回的 **LSN / GTID 水位线**，从库只有追平到该 LSN 才响应。

### 2. 脑裂（Split-Brain）：双主同时写入的灾难

网络抖动导致从库连不上主库，如果两套监控各自以为对方挂了，把从库提升为“新主库”，而老主库依然在接收部分客户端写入——网络恢复后，**两个主库各自写了冲突的数据，彻底无法合并！**
**防线**：绝不靠“互相 ping 不通就单方面升主”，必须依赖**多数派 Quorum 选主（如 Raft / etcd / Patroni，至少 3 节点奇数组成集群，少数派侧无法过半自动降级只读）** + **Fencing Token（递增任期号 + STONITH 断电隔离旧主）**。

## 十、水平分片（Sharding）与一致性哈希 (DB-49)

当单机主库的写入 QPS 或磁盘容量达到物理天花板时，单库垂直升级（Scale-Up）已经买不到更大的机器，必须把一张大表拆散存到多台独立数据库实例（**水平分片 Horizontal Sharding**）。

### 1. 范围分片 vs 哈希分片 vs 一致性哈希

- **按范围分片（Range Sharding）**：`id 1~1000万` 放库 A，`1000万~2000万` 放库 B（或按月分库）。范围查询极其友好，但**如果按时间或自增 ID 分片，最新写入流量 100% 砸在最后一台机器上（写入热点）**！
- **简单取模哈希（`hash(key) % N`）**：写入打散极均匀；但当 3 台机器扩容成 4 台时，`key % 3` 变成 `key % 4`，**约 75% 的全库数据都要跨网络大搬家**！
- **一致性哈希（Consistent Hashing + 虚拟节点）**：把 `0 ~ 2^32 - 1` 弯成一个哈希环，物理节点映射成几百个虚拟节点（Virtual Nodes，解决节点少时负载不均）均匀插在环上，数据顺时针落到最近的节点。扩容新增节点时，**只有平均 $1/K$ 的数据需要从相邻节点迁走**！

```text
一致性哈希环（0 ~ 2^32 - 1）:
             [Node A #1]
            /           \
    [Data X]             [Node B #1]
          |               |
    [Node C #1]          [Data Y] ──▶ 顺时针归属 Node C #2
            \           /
             [Node C #2]
```

### 2. Shard Key（分片键）选择是分片成败的命门

选错 Shard Key，几乎所有查询都要广播扫描全部 16 个分片（Scatter-Gather）且处处是跨库分布式事务！
**第一铁律**：按高频业务聚合实体选 Shard Key——例如电商系统选 `user_id` 做分片键，让同一个用户的 `orders` 和 `order_items` 落在**完全同一个物理分片**里，这样查个人订单和下单扣减都能退化成极快的单机本地事务和单机 `JOIN`！

## 十一、分布式事务：2PC（两阶段提交）、Outbox 与 Saga (DB-50)

一旦业务必须同时修改**两个物理隔离的数据库**（如“订单库扣款创建订单” + “库存库扣减库存”），本地 `BEGIN ... COMMIT` 就管不到对面库了。工程上主要有两大流派：

### 1. 强一致刚性事务：2PC（Two-Phase Commit / XA）

```text
协调者 (Coordinator)              参与者 A (订单库)        参与者 B (库存库)
   │ ── 1. Prepare (准备阶段) ──▶  [拿锁写本地Redo，不提交!]  [拿锁写本地Redo，不提交!]
   │ ◀─ 2. Vote Yes / No ──────    返回 Ready                返回 Ready
   │ ── 3. Commit (提交阶段) ───▶  正式 COMMIT 释放锁        正式 COMMIT 释放锁
```

**2PC 的三大致命痛点**：
1. **同步阻塞**：从第 1 阶段 Prepare 到第 2 阶段结束，所有参与者一直死死攥着行锁，吞吐暴跌！
2. **协调者单点阻塞故障**：如果协调者在发出 `Prepare` 收到所有人 `Yes` 后突然宕机，参与者既不敢擅自提交也不敢回滚，**锁会无限期挂死**！
3. **跨机房网络延迟放大**：两次 RTT 往返，任一节点抖动拖垮整条链路。

### 2. 高并发柔性最终一致：Transactional Outbox 与 Saga 模式

现代微服务高并发系统 90% 以上放弃 2PC，转用**最终一致性（BASE）**：

1. **事务性发件箱（Transactional Outbox）**：解决“本地改库成功了，发 MQ 消息却网络超时怎么办？”——把业务表更新和一条待发事件 `INSERT INTO outbox(...)` **塞进同一个本地 ACID 事务提交**！后台独立 Relay 线程轮询（或通过 CDC 读 Binlog）把 Outbox 消息可靠投递到 MQ，消费者做好幂等去重即可。
2. **Saga 模式（长活事务拆解 + 反向补偿）**：把跨 3 个服务的长事务拆成一串独立本地 ACID 事务 $T_1 \rightarrow T_2 \rightarrow T_3$；万一 $T_3$ 失败，按反方向执行**业务补偿事务** $C_2 \rightarrow C_1$ 把前面冲正回来！
   - **编排式（Orchestration）**：由一个中心状态机协调器统一指挥调用与补偿（流程清晰易排查，工程首选）。
   - **协同式（Choreography）**：各服务互相订阅发布事件链式触发（无中心节点，但链路长了极难追踪）。
   - **Saga 的三大工程铁律**：
     1. 补偿操作 $C_i$ **必须支持幂等且允许空补偿/防悬挂**（网络重试时可能收到多次补偿请求，或补偿比正向请求先到！）；
     2. **Saga 没有全局隔离性（Isolation）**！$T_1$ 提交后在 $T_3$ 完成前，中间状态对外部可见——因此通常配合**语义锁（如先置状态为 `PENDING_RESERVE` 冻结额度，全部成功再转 `CONFIRMED`）**；
     3. 正向或补偿请求全靠唯一 `idempotency_key` 防重。

## 本课常见 1 行反例坑（对照排查）

- 以为只要用了数据库的 `REPEATABLE READ`，业务代码写 `x = read(); write(x - 10);` 就绝对安全 → 快照读加应用层算减法依然会**丢失更新**或**写偏斜**！必须用单句原子更新 `UPDATE ... SET x = x - 10 WHERE x >= 10` 或 `FOR UPDATE` / 乐观锁 `version`。
- InnoDB 里执行 `UPDATE t SET ... WHERE unindexed_col = 'x'` → 没有索引导致锁住聚簇索引全表所有行和所有间隙，瞬间引发全站雪崩阻塞。
- 认为只要给业务加了读写分离，就能把所有读全丢给从库 → 主从复制延迟让用户“刚下单刷新页面却显示没订单”，需按业务配置写后读路由主库。
- 觉得加分布式锁或 2PC 就能一劳永逸解决跨库问题 → 2PC 协调者崩溃会永久卡死行锁，高并发跨服务应优先考虑 **Outbox + Saga + 幂等键**。
- 在没有固定加锁顺序的情况下，多行互转账户（A 转 B 与 B 转 A 并发） → 必出死锁环；务必按 `min(id)` 到 `max(id)` 排序后再加锁。

## 5 个梯度微练习

### 练习 1（ReadView 可见性手算）

在 MySQL InnoDB `REPEATABLE READ` 下，某行记录当前最新版的 `trx_id = 105`。事务 `T108` 刚开启时，系统里活跃（未提交）的事务有 `[102, 105, 108]`，下一个待分配 ID 为 `110`。请问 `T108` 执行普通 `SELECT` 时，能看到 `trx_id = 105` 这个版本吗？如果看不到，它会怎么做？

<details>
<summary>核对答案</summary>

`T108` 的 ReadView 中 `m_ids = [102, 105, 108]`，`min_trx_id = 102`，`max_trx_id = 110`。
比对 `trx_id = 105`：它既不等于 `108`，又落在 `[102, 110)` 区间内，且 **`105` 在 `m_ids` 活跃列表里**（说明拍照瞬间 `T105` 还没提交）——因此**不可见**！引擎会沿着该行的 `roll_ptr` 去 Undo Log 里继续往回找，直到遇到一个 `trx_id < 102` 或不在 `m_ids` 里的已提交旧版本为止。

</details>

### 练习 2（死锁排查与消除）

请写出下面两段并发 SQL 必然触发死锁的交叉时间线，并给出零改动表结构的一行代码级预防修复：
- 请求 1：`transfer(from=10, to=20, amt=50)`
- 请求 2：`transfer(from=20, to=10, amt=30)`

<details>
<summary>核对答案</summary>

交叉时间线：
1. 请求 1 锁住 `id = 10`；
2. 请求 2 锁住 `id = 20`；
3. 请求 1 尝试锁 `id = 20`（阻塞等请求 2）；
4. 请求 2 尝试锁 `id = 10`（阻塞等请求 1）→ 死锁环形成，数据库被迫回滚其中一个！
**一行预防修复**：在函数入口处强制按账号 ID 从小到大加锁（先锁 `std::min(from, to)`，再锁 `std::max(from, to)`），两方永远先抢 `10` 再抢 `20`，彻底消灭环路。

</details>

### 练习 3（乐观锁 SQL 设计）

某抢购商品表 `items(id, stock, version)`，初始 `stock = 1, version = 10`。请写出一条不用 `SELECT ... FOR UPDATE` 悲观锁、基于乐观锁防超卖的原子 `UPDATE` 语句，并说明应用层如何判断自己抢购成功还是失败？

<details>
<summary>核对答案</summary>

```sql
-- 先普通查出 version = 10 且 stock > 0，再执行 CAS 原子更新：
UPDATE items
SET stock = stock - 1, version = version + 1
WHERE id = 1001 AND version = 10 AND stock > 0;
```
应用层检查数据库连接返回的 **`affected_rows`（受影响行数）**：等于 `1` 表示抢购成功；等于 `0` 说明要么库存已经归零，要么被别人抢先一步把 `version` 改成了 `11`，应用层直接提示失败或重读重试即可（也可直接不带 `version` 靠 `WHERE id = 1001 AND stock > 0` 单句原子扣减实现更高并发！）。

</details>

### 练习 4（WAL 与 ARIES 恢复思考）

在 ARIES 崩溃恢复的三阶段里，为什么 **Redo（重做）阶段** 要把后来其实没提交的 Loser 事务的改动也先重放一遍，而不是直接跳过它们？

<details>
<summary>核对答案</summary>

因为 Buffer Pool 采用物理页级刷脏（Steal 策略）且操作可能共享同一个物理数据页，Redo 日志记录的是基于当时物理页布局（如页内偏移、空闲空间、LSN）的生理更新。如果不从最早脏页的 `recLSN` 开始按顺序**完整重演历史（Repeating History）**先把物理页状态精确还原到崩溃那一微秒，后面的 Undo 逆向恢复和并发同页上的已提交修改就无法对应正确的物理页前提与 LSN 序列。

</details>

### 练习 5（分布式 Saga 幂等与语义锁）

在“下单（订单服务） → 扣余额（账户服务） → 扣库存（库存服务）”的 Saga 流程中，如果在等待库存扣减期间，用户又发起了另一笔下单，发现账户余额因为还没扣减完而虚高，或者超时重试导致扣了两次钱，应该用哪两个工程机制兜底？

<details>
<summary>核对答案</summary>

1. **语义锁 / 冻结预留（对抗缺乏全局隔离性）**：账户扣款不要直接做一次性扣减或放任并发，而是先冻结额度（`frozen_balance += amt`、`available_balance -= amt`）或将订单置为 `PENDING` 中间状态；全部成功再确认解冻核销，失败则执行补偿解冻。
2. **全链路 `idempotency_key` 幂等表**：每一笔正向请求和补偿请求都携带全局唯一的 `(order_id, action)` 幂等键在目标服务库内建唯一约束，防止网络超时重试导致扣两次钱或重复补偿。

</details>
