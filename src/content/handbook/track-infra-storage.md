## 本篇总览（TRK-23 ~ TRK-32）

基础架构（Infrastructure / 数据库内核 / 分布式存储 / 中间件）是 C++ 含金量最高的方向之一——别人“调数据库和缓存”，而你负责**亲手造出高可靠存储与分布式协调引擎**。本篇打通 `TRK-23` ~ `TRK-32`。

---

## 一、系统与中间件岗位核心关注点（TRK-23）

相比普通业务后端，基础架构工程师几乎天天和以下四大硬问题打交道：
1. **极致数据持久性**：进程随时可能 `kill -9` 或机房断电，如何在 **顺序追加写磁盘** 上建出崩后瞬间恢复的数据结构？
2. **绕开操作系统黑盒**：通用 `malloc` 碎片高、Page Cache 双重缓冲不受控、内核线程锁竞争——自己管好每一页内存（Buffer Pool）与分配器（Arena）。
3. **写放大、读放大、空间放大三角博弈**：任何存储引擎都无法同时三项全最小，必须清楚业务读写比。
4. **多副本一致性与扩缩容**：3 台或 5 台机器之间网络会丢包、分片会扩容，如何保证任何一台挂掉对外依然读不到旧脏数据？

## 二、高性能自研分配器：Arena、Slab 与 Buddy（TRK-24）

| 分配器类型 | 工作原理 | 核心优势与适用场景 |
| --- | --- | --- |
| **Arena（区域线性分配器）** | 提前申请 4MB 大块内存，内部只维护一根 `offset` 指针，`alloc(n)` 就是 `ptr += n`（**1 条加法指令！**），整块用完一次性全释放 | 零碎片、极速分配；极适合“一个请求/一个 MemTable”生命周期统一销毁的对象 |
| **Slab / 对象池** | 预先把大页切好成百上千个固定大小槽位（如 64B、128B），用单向空闲链表 `free_list` 串联 | 彻底消灭外碎片与大小锁；Linux 内核对象分配器、游戏组件池 |
| **Buddy（伙伴系统）** | 按 $2^k$ 大小对半分裂内存块，相邻同尺寸空闲兄弟释放时可瞬间合并回大块 | 减少大块连续物理内存外部碎片（Linux 物理页帧管理底座） |

## 三、Buffer Pool 管理器与 Clock / LRU-K 淘汰（TRK-25）

数据库文件动辄几百 GB，但内存只有几十 GB。**Buffer Pool（缓冲池）**就是在用户态自己划出几万个固定 4KB/16KB 页框（Frame）构成的数组：
- **Pin / Unpin 引用计数**：只要有线程正在读某页，必须把该页 `pin_count++` 钉在内存里，绝不能在别人读取到一半时把它淘汰换出！
- **为什么纯 LRU 在数据库里会遭“全表扫描污染”？** 假如一次全表 `SELECT *` 扫过 100 万页冷数据，会把普通 LRU 里真正高频的热点索引页全挤出内存！
- **解法：LRU-K（如 LRU-2）或 Two-Queue / Clock-Sweep**：只有**最近访问至少达到 $K=2$ 次**的页才能晋升到热区链表；只偶遇 1 次的冷页留在历史考察队列里迅速淘汰，保护热数据岿然不动！

## 四、WAL（预写日志）与 Group Commit 组提交（TRK-26）

直接把每次修改随机写回 100GB 数据文件里 B+ 树各个位置，机械盘直接卡死、SSD 也寿命骤减；且万一写到一半断电树结构彻底损坏。
**WAL 黄金铁律**：任何数据页改动**落盘前必须先把简短的操作日志（Redo Record）顺序追加写进 WAL 文件并调用 `fdatasync`**！顺序写磁盘速度比随机写快几十上百倍。
- **Group Commit（组提交）**：单线程一次 `fsync` 等盘转需要 0.5~5ms，每秒最多只能提交几百次事务！让**同时到达的 64 个并发事务的 WAL 日志先合并塞进同一个大缓冲，只调用 1 次 `fsync` 集体刷盘再一起通知成功**——`fsync` 摊薄 64 倍，TPS 瞬间暴涨几十倍！

## 五、KV 存储引擎两条路线：Bitcask 哈希日志 vs LSM-Tree（TRK-27）

| 架构流派 | 代表引擎 | 内存与磁盘核心设计 | 强项与致命短板 |
| --- | --- | --- | --- |
| **Bitcask 模型** | Riak、早年简单 KV | 磁盘永远只顺序追加写 Log；**内存维护一个全量哈希表 `{Key -> (文件ID, 偏移, 大小)}`**，定期后台合并旧文件 | 写极快（1 次顺序写），读极快（只需 1 次磁盘寻道）；**短板：所有 Key 必须全部塞进内存**，且不支持范围扫描 `Range Scan`！ |
| **LSM-Tree 模型** | **RocksDB / LevelDB / Cassandra** | 写入先进内存有序 **MemTable（跳表）+ WAL**；满后冻结刷成磁盘只读有序 **SSTable** | 吞吐天花板极高，支持范围扫描且 Key 无需全在内存；**短板：读可能要跨多层 SSTable 找（需布隆过滤器救场）**，且后台 Compaction 存在写放大 |

## 六、SSTable 合并（Compaction）与布隆过滤器（TRK-28）

LSM-Tree 不断刷出 L0、L1、L2 多层有序 SSTable，删除只是追加写入一条**墓碑标记（Tombstone）**。如果永远不整理，磁盘爆满、查一个不存在的 Key 要翻遍几十个文件！
1. **Compaction（合并压缩）**：后台线程定期把重叠区间的小文件多路归并成一个干净的新大文件，顺带**彻底物理清理被覆盖的旧值和墓碑**（主要分 Size-Tiered 适合写多与 **Leveled Compaction** RocksDB 默认、控空间放大 1.1x）。
2. **布隆过滤器（Bloom Filter）**：查不在库里的 Key 时，先过一遍只有几 MB 的全内存二进制位图（经过 $k$ 个独立哈希置位）。**如果布隆过滤器说“不在”，则 100% 确定该 SSTable 里绝无此 Key，省掉昂贵磁盘读取！**（若说“可能在”，可能有约 1% 假阳性再去查磁盘索引）。

## 七、分布式共识 Raft 直观理解：选主与日志复制（TRK-29）

单机硬盘总会坏，生产存储必须存 3 份以上副本。**Raft** 把复杂分布式一致性拆成两个清晰子问题：
1. **Leader Election（领导者选举）**：集群同一时刻至多只有 1 个受**多数派（$N/2 + 1$，例如 3 节点至少 2 票）**承认的 Leader（靠随机化选举超时定时器防止瓜分选票打平）；一切写请求必须找 Leader。
2. **Log Replication（日志复制）**：Leader 收到写请求后先写进自己本地日志，再并发发给 Follower；**只要收到多数派（包括自己 ≥ 2 台）确认落盘，这条日志就标记为 `Committed` 可安全回客户端成功！**哪怕此时挂掉 1 台机器，剩下的节点里必定至少有 1 台拥有全部已提交日志能选成新 Leader，绝不丢已确认数据！

## 八、一致性哈希与分片扩缩容（TRK-30）

数据太多单机装不下，如果简单用 `hash(key) % N` 分到 `N=3` 台机器，突然加 1 台机器变成 `% 4` 时，**几乎 75% 的老数据全都要跨机房大搬迁**，瞬间打爆缓存和数据库！
**一致性哈希（Consistent Hashing）**：把哈希值范围 $[0, 2^{32}-1]$ 弯成首尾相接的圆环。每台物理机器通过引入**几百个虚拟节点（Virtual Nodes）**均匀插在环上；每条数据按自己顺时针往下摸到的第 1 个节点落盘。扩容 1 台机器时，**平均只需迁移 $1/(N+1)$ 的极少相邻切片**，而且虚拟节点彻底消除了节点数量少时的数据倾斜！

## 九、分布式缓存三大雪崩级危机与防线（TRK-31）

| 故障名称 | 发生机制（怎么打穿数据库的？） | 工业级标准解法 |
| --- | --- | --- |
| **缓存穿透** | 恶意请求大量查**根本不存在**的 ID `-999`，Redis 永远 Miss，流量直接灌死 DB！ | 缓存空对象（短 TTL） + **布隆过滤器前置拦截**不存在 ID |
| **缓存击穿** | 某个**超级热点 Key**（如顶流明星新闻）刚好到期瞬间失效，一万个并发同时穿透打向 DB 重建 | **热点永不过期逻辑异步续期** + 单飞模式 **Singleflight / 互斥锁**只放 1 个人去 DB 回源 |
| **缓存雪崩** | 成千上万个 Key 设了完全相同的 TTL 在同一秒集体过期，或者整个 Redis 实例宕机 | **TTL 加随机抖动打散** + 多级本地内存缓存 + 限流降级保 DB 不死 |

## 十、可靠异步任务队列与事务发件箱（Transactional Outbox，TRK-32）

如果接口需要“先把订单写入 MySQL，再发一条 Kafka/MQ 消息通知积分系统”——万一刚写完 MySQL 进程崩了没来得及发 MQ，数据就永久不一致！
**Transactional Outbox 模式**：在**同一个本地数据库事务**里，同时往业务表插订单、往 `outbox_events` 待发事件表插一条记录；再由一个后台 Worker（或 CDC 订阅 Binlog）轮询 `outbox_events` 发向 MQ 并依赖下游**幂等键去重（At-Least-Once + Idempotent Consumer）**，用极简工程代价做到绝不丢消息！

## 十一、微练习与自检

1. 如果 3 节点 Raft 集群在网络分区下被劈成 `[Node1]` 与 `[Node2, Node3]` 两半，客户端向孤立的 `Node1` 发起写入请求能成功提交吗？为什么？
2. 某系统往 Redis 塞了 10 万条商品数据，半夜 0 点整统一刷新失效时间设成了整 24 小时，第二天半夜 0 点数据库突然 CPU 100% 宕机，这是上述哪类故障，怎么一句话修好？

<details>
<summary>核对答案</summary>

1. **不能！** 3 节点集群多数派门槛为 $\lfloor 3/2 \rfloor + 1 = 2$ 票。孤立的 `Node1` 凑不够 2 个副本确认，绝对无法提交（从而保证另一侧 `[Node2, Node3]` 选出新主后不会产生数据脑裂）。
2. 这是典型**缓存雪崩**（大量 Key 同时到期）。修复方式是在基础 TTL 上加一个随机抖动偏移（如 `86400 + rand() % 1800`），把到期压力平摊开；核心热点可加 Singleflight 防并发穿透重建。

</details>
